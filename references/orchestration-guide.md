# 编排指南（Orchestration Guide）

> 版本：v26.6.21.1305（草稿，阶段 0 冻结）  
> 用途：run-dd 编排模式的规则手册。描述 Loop A/B 循环逻辑、full/staged 模式选择规则、强制人工断点清单，以及状态机 schema。  
> 与 acceptance-criteria.md 配套：编排指南定义"什么时候该做什么"，验收标准定义"做完了没有"。

---

## 一、整体架构分层

```
L0 目标层：律师下达一次目标（材料夹 + 项目信息 + 验收要求）
    │
    ▼
L1 编排层（run-dd 总控）
    ├─ Loop A  intake → adjudicate（资料齐备性核验 + 律师终裁）
    ├─ Loop B  update（增量推进：定位受影响章节 → draft --mode incremental）
    └─ 推进闸门（以律师认定为准）→ check → report
    │
    ▼
L2 能力层（原四模式）：init / draft / check / report
    + intake / adjudicate / update（新增）
    + yd-enterprise-info（自动调用）
    │
    ▼
L3 状态与验收层
    ├─ task-board.md         章级状态机
    ├─ dd-checklist.md       双轨尽调清单（AI研判轨 + 律师认定轨）
    ├─ materials-ledger.md   资料台账（批次留痕）
    └─ adjudication-log.md   认定台账（认定/改判留痕）
```

---

## 二、run-dd 循环逻辑骨架

```
输入：材料夹路径、目标公司、委托人、基准日、目的、(可选)USCC、运行模式(full/staged)
──────────────────────────────────────────────────────────
1. PLAN
   a. init：建项目目录结构（task-board、dd-checklist、materials-ledger、adjudication-log）
   b. 扫描材料夹，调用 reconcile_materials.py 生成章节-材料映射表
   c. 若提供 USCC → 规划 yd-enterprise-info 拉取计划
   d. 写入 task-board.md（各章初始状态=未开始）

2. LOOP A — 资料齐备性核验
   a. reconcile 脚本比对清单 → 写 AI 研判轨（AI研判/AI置信/需复核）
   b. 生成 研判报告-第k批.md（仅展开"需复核"项）
   c. ★ 强制人工断点（CP-6）：adjudicate 模式汇总"需复核"项 → 律师终裁 → 写律师认定轨 + 写 adjudication-log
   d. 闸门检查：高重要项律师认定是否全部 ∈ {已齐备, 不适用, 豁免}
      - 是 → 可推进 LOOP B / 定稿
      - 否 → 出"待补充资料清单"，等下一批（staged 模式到此停止；full 模式可继续写未受阻章节）

3. LOOP B — 章节撰写与增量推进
   对每一章（可并行，落盘时串行）：
   a. 读对应材料 + 已落地工商数据
   b. 若有 USCC 且该章在 external-apis.md 中有适用接口 → 自动拉取 yd-enterprise-info 数据
   c. draft（全量首次）或 draft --mode incremental（增量重做）
   d. 章级自检（acceptance-criteria.md AC-C1–AC-C7）
      - 全通过 → 更新 task-board 该章状态=已自检
      - 未通过 → 自动补写，最多重试 2 次；仍未通过 → 状态=待人工，进断点清单

4. CHECK
   a. 自动跑完整性检查，汇总缺失材料与风险
   b. 能自动补的（公开数据）→ 回 LOOP B；不能补的 → 进断点清单

5. CHECKPOINT（强制人工断点汇总）
   汇总所有 task-board 状态=待人工 的事项 → 律师逐项处置
   等律师答复后继续（staged 模式在此停止；full 模式处置完继续）

6. REPORT
   闸门检查（AC-P1–AC-P5 全通过）→ 生成报告
   报告免责声明：取 dd-checklist 律师认定=部分-需补/待认定 的项，自动写入"限制条件与免责声明"

7. FINAL VERIFY
   底稿与报告一致性终检 → 输出遗留问题清单 + 本次循环日志
```

**重要约束**：
- 每次自动动作（调 API、自检重写、reconcile 比对）均记入循环日志（时间、动作、依据、结果）
- 系统自动整合的内容标注"系统自动整合，待律师复核"
- 凭证（CHINESELAW_API_KEY 等）只走环境变量，绝不写入任何项目文件

## 三、full / staged 选择规则

| 模式 | 含义 | 退出时机 | 适用场景 |
|------|------|---------|---------|
| **staged（默认）** | 每批料只推进到当前能做的程度，出阶段性底稿+待补清单后停止 | 每批料的 LOOP A 认定完成 + 当批受影响章节增量完成 | 材料分批到位、需阶段性交付 |
| **full** | 一口气把当前材料跑到底（check → report），遇强制断点停 | FINAL VERIFY 完成，或遇强制断点 | 材料基本齐备、需快速出完整初稿 |

**默认行为**：用户未指明时，默认 staged，并提示"如需一次性跑完当前材料请说'完整模式'"。  
**共用状态**：两模式共用 task-board / dd-checklist / adjudication-log，可中途切换。

## 四、强制人工断点（Human-in-the-Loop Checkpoints）

以下任一情形触发，AI 必须**停下来汇总、不得自行判定、不得跳过**：

| # | 断点名称 | 触发条件 | AI 做什么 |
|---|---------|---------|---------|
| CP-1 | 关键材料缺失 | 某章所需"重要程度=高"的材料均未取得，导致无法对本章发表任何意见 | 汇报缺失项及影响，等律师指示是否继续 |
| CP-2 | 高风险事项 | 底稿 §X.5 出现 🔴 高风险 | 列出高风险项（包含事实依据与法律依据），等律师处置指示 |
| CP-3 | 法律定性存疑 | 某安排的性质存在歧义（如是否构成代持/抽逃出资/违规担保等），AI 无法唯一定性 | 描述歧义点与各种定性的依据，等律师拍板 |
| CP-4 | 数据冲突 | 外部 API 数据与目标公司提供材料不一致 | 列出冲突点（两个来源各自说了什么），等律师认定以哪个为准 |
| CP-5 | 对外承诺 / 意见措辞 | 任何需要"对外承诺"或"出具正式意见"的措辞 | 停止，由律师审定措辞后方可继续 |
| **CP-6** | **资料齐备性认定** | **每批 reconcile 完成后，需要律师认定各项是否齐备** | **汇总"需复核"项 → adjudicate 模式 → 律师终裁；AI 绝不自行判定齐备** |

> **CP-6 是本版新增，属于 Loop A 的必经节点**，不可因"效率"原因跳过或削弱。  
> AI 研判（AI研判/AI置信）只是建议，律师认定才是推进闸门的依据。

## 五、推进闸门规则

```
可推进 check/report ⟺ 满足以下全部条件：
  1. task-board 无"待人工"章节（或已由律师书面豁免）
  2. dd-checklist 所有"重要程度=高"项，律师认定 ∈ {已齐备, 不适用, 豁免}
  3. adjudication-log 无未消解的 ⚠️ 冲突项

注意：闸门判断依据是"律师认定"列，而非"AI研判"列。
```

## 六、状态机 schema（task-board.md 每章字段）

冻结字段（阶段 0 固定，后续不得随意增删字段名）：

| 字段 | 类型 | 说明 |
|------|------|------|
| 章节 | string | 章节编号 + 名称，如"第1章 公司基本信息与主体资格" |
| 状态 | enum | 见下方枚举 |
| 数据基准批次 | string | 截至第 k 批；初始空，首次 draft 后写入 |
| 受影响 | bool | 本轮新批次是否需重做（reconcile 后自动更新） |
| 断点事项 | text | 当前未消解的断点描述；空=无断点 |
| 自检备注 | text | AC-C1–AC-C7 的自检结果摘要 |

**状态枚举**（完整、无歧义）：

```
未开始     → 章节尚未启动
进行中     → 正在撰写
已自检     → AC-C1–C7 全通过，待律师复核
待人工     → 触发断点，需律师介入
已完成     → 律师人工复核通过，本章定稿
```

## 七、dd-checklist 双轨字段 schema（冻结）

冻结字段顺序与枚举，供 reconcile_materials.py、adjudicate 模式、init 脚本共同遵守：

```
| 编号 | 资料项 | 章节 | 重要程度 | AI研判 | AI置信 | 需复核 | 律师认定 | 认定人 | 认定日期 | 律师批注 | 本项齐备标准 | 最近批次 |
```

**AI 轨字段**（仅脚本/AI可写）：

| 字段 | 枚举值 | 说明 |
|------|--------|------|
| AI研判 | ✅已收 / 🟡部分 / ❌未收 / ⚪疑似不适用 | 脚本匹配结果 |
| AI置信 | 高 / 中 / 低 | 高=强匹配且数量/年度完整；中=部分/版本不全；低=弱匹配/一文对多项 |
| 需复核 | 是 / 否 | 按"需复核自动置位规则"（见下 §八）由脚本置位 |

**律师轨字段**（仅律师经 adjudicate 写入，任何脚本/自动流程禁止改写）：

| 字段 | 枚举值 / 格式 | 说明 |
|------|-------------|------|
| 律师认定 | **待认定**（默认） / 已齐备 / 部分-可推进 / 部分-需补 / 不适用 / 豁免 | 权威状态，绝不默认"已齐备" |
| 认定人 | string | 经办律师姓名 |
| 认定日期 | YYYY-MM-DD | 认定时间 |
| 律师批注 | text | 认定理由、项目特定要求、"批量采纳 AI 建议，YYYY-MM-DD"等 |
| 本项齐备标准 | text | 本项目对该项"算齐备"的具体口径（可覆盖通用默认） |

**其他字段**：

| 字段 | 格式 | 说明 |
|------|------|------|
| 重要程度 | 高 / 中 / 低 | 清单模板预填，律师可调整 |
| 最近批次 | 第k批 | reconcile 时自动更新 |

## 八、"需复核"自动置位规则（供 reconcile_materials.py 实现）

以下任一情形，脚本必须将该项 `需复核` 置为"是"：

1. `AI置信 ∈ {中, 低}`
2. `重要程度=高` 且 `AI研判 ≠ ✅已收`
3. 某项 `律师认定=已齐备`，本批新料显示该项实际不一致/有缺 → 标 `需复核=是` + 在研判报告标 ⚠️ 与既有律师认定冲突，**不修改律师认定**
4. 律师此前标"不适用/豁免"，但本批出现该类材料（可能需重新纳入）
5. 文件无法归类（待人工归类项）

**未触发"需复核"的项**：律师可一次性"批量采纳 AI 研判"，系统在律师批注标"批量采纳 AI 建议，YYYY-MM-DD"，保留可追溯。

## 九、adjudication-log.md 行结构（冻结）

```
| 时间 | 编号 | 资料项 | 原认定 | 新认定 | 认定人 | 理由/依据 | 触发批次 |
```

每次认定（含批量采纳）、改判，均追加一行，不修改已有行。

## 十、不猜归类原则

匹配不确定的材料一律进"待人工归类"列表，不得推断归类后默默写入 dd-checklist。  
本原则是硬约束，不因"材料名称近似"而例外。

## 十一、留痕要求

| 事件 | 记录位置 |
|------|---------|
| 每批资料核验 | materials-ledger.md 追加一行；研判报告-第k批.md 新建 |
| 每次 adjudicate 认定/改判 | adjudication-log.md 追加一行 |
| 每次增量底稿改动 | 循环日志（run-dd-log.md）追加；底稿 §X.4 标注"据第k批更新" |
| API 调用 | 成功：raw/chineselaw/ 落盘；失败：§X.6 律师备忘记录时间与原因 |
